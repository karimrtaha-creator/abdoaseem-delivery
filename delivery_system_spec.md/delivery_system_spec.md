# مواصفات نظام إدارة التوصيل والشكاوى - سلسلة مطاعم عبده عاصم (ABDO ASEEM) - 13 فرع

> **ملاحظة لأي مبرمج أو أداة برمجة (زي Claude Code) هتبدأ التنفيذ:**
> ده مستند مواصفات كامل لنظام إدارة توصيل وطلبات لسلسلة مطاعم بها 13 فرع. اقرأ المستند كامل قبل أي كود. ابدأ بالمرحلة 1 في قسم "خطة التنفيذ المرحلية" (تطبيق الطيار + الديسباتشر + حساب SLA)، ثم المرحلة 2 (شاشة الكول سنتر + لوحة قبول الأوردرات)، وهكذا بالترتيب. كل الأدوار والجداول والـ Enums موصوفة بالتفصيل في الأقسام التالية - لو أي تفصيل ناقص أو غامض، اسأل بدل ما تفترض.

## 1. نظرة عامة على الهدف

بناء نظام (ويب سايت + تطبيق موبايل للطيار) لحل 3 مشاكل:
- تأخيرات التوصيل غير المرصودة
- شكاوى العملاء بدون مصدر واضح للمشكلة
- غياب رؤية موحدة للمدير على الـ 13 فرع

**المخرج النهائي:** كل أوردر له "بصمة زمنية" كاملة (طلب → قبول → تجهيز → خروج → تسليم)، وكل تأخير أو شكوى مربوطة تلقائيًا بالطيار والفرع المسؤول، عشان تقدر تحاسب بدقة بدل التخمين.

**نقطة أساسية:** النظام يفصل بوضوح بين مسؤوليتين مختلفتين:
- **وقت التحضير** (من الطلب لحد تسجيل خروج الأوردر من الديسباتشر مع صورة الرسيت) → مسؤولية الفرع/المطبخ.
- **وقت التوصيل** (من لحظة الخروج لحد التسليم بالـ OTP) → مسؤولية الطيار حصريًا.

هذا الفصل يمنع الخلط بين "مين فعليًا سبب التأخير" ويعطي تقارير دقيقة لكل طرف.

**منطق الصلاحيات (Permissions Logic):**

| الدور | يشوف/يدير أوردرات وطيارين | يقدر يضيف/يعدّل مستخدمين |
|---|---|---|
| `general_manager` | كل الفروع بدون استثناء | أي مستخدم، في أي فرع أو منطقة |
| `team_leader` | كل الفروع بدون استثناء - **للمتابعة وقبول الأوردرات فقط** (نفس نطاق رؤية المدير العام، لكن بدون صلاحية إدارة المستخدمين/الفروع) | لا يقدر يضيف/يعدّل مستخدمين |
| `regional_manager` | كل الفروع التابعة لـ `region_id` بتاعه فقط | موظفين الفروع التابعة لمنطقته فقط (مايقدرش يضيف حد في فرع خارج منطقته) |
| `branch_manager` | فرعه (`branch_id`) بس | موظفين فرعه فقط |

هذا يعني أن كل استعلام (Query) في لوحة المدير أو شاشة إدارة المستخدمين لازم يُفلتر تلقائيًا حسب دور المستخدم المسجّل دخوله (Row-Level Security بسيطة على مستوى الـ Backend): لو `regional_manager`، الفلتر = `branch.region_id = user.region_id`؛ لو `branch_manager`، الفلتر = `branch_id = user.branch_id`.

**قاعدة عزل صارمة (Strict Data Isolation):** لا يوجد أي شاشة أو تقرير يسمح بمقارنة أو عرض أرقام خارج النطاق المسموح للمستخدم - حتى لو كانت أرقام مجمّعة أو مجهّلة (Anonymized). يعني:
- مدير فرع مايشوفش ولا رقم واحد عن أي فرع تاني، ولا حتى "متوسط كل الفروع" لو ده هيدّيه فكرة عن أداء فروع تانية.
- مدير منطقة يشوف فروع منطقته كأرقام منفصلة (مش مجمّعة في رقم واحد بس، لأنه محتاج يفرق بين فروعه)، لكن **صفر رؤية** لأي فرع أو منطقة برا نطاقه.
- هذا القيد لازم يتطبق على مستوى الـ API نفسه (الباك إند يرفض الطلب لو حاول أي مستخدم يطلب بيانات خارج نطاقه، مش بس إخفاء العناصر في الواجهة)، عشان محدش يقدر يتحايل عن طريق تعديل الطلب مباشرة (API Call) لمعرفة أرقام مش من حقه يشوفها.

## 4. منطق حساب التأخير (SLA Logic) - الأهم

```
عند إنشاء الأوردر (order_time):
  الأوردر يبدأ بحالة pending_acceptance (بانتظار القبول)
  - سواء جاي من الكول سنتر، تطبيق العميل، أو الكاشير

عند مراجعة الأوردر من تيم ليدر/هيد مانجر:
  لو payment_method = instapay_transfer:
    يتحقق من صورة إثبات التحويل (payment_proof_url) قبل القبول
  يضغط "قبول الأوردر":
    accepted_by = المستخدم الحالي (team_leader أو general_manager)
    accepted_at = NOW()
    الأوردر يتحول لحالة preparing
  أو يضغط "رفض الأوردر" (مثلًا بيانات ناقصة أو إثبات دفع غير واضح):
    الأوردر يتحول لحالة rejected ويُبلَّغ العميل/الكول سنتر

عند تجهيز الأوردر وطباعة الرسيت:
  الديسباتشر يفتح شاشة "تسجيل خروج الأوردر":
    - يختار الطيار
    - يدخل رقم الأوردر وسعر التوصيل بعد الضريبة (من الرسيت المطبوع)
    - يصوّر الرسيت (دليل إثبات، مش مصدر بيانات يُقرأ آليًا)
    - يضغط "تأكيد الخروج"

  عندها فقط:
    dispatch_time = NOW() [وقت السيرفر، وليس وقت الموبايل]
    prep_time_minutes = dispatch_time - accepted_at
    sla_minutes = مطابقة delivery_fee_after_tax مع جدول sla_tiers
    (مثال: سعر توصيل 24 جنيه → يقع بين 20.01-25 → sla_minutes = 40)
    الأوردر يتحول لحالة out_for_delivery
    يبدأ عداد تنازلي في تطبيق الطيار = sla_minutes

عند تأكيد الـ OTP (delivered_time = NOW()):
  delay_minutes = (delivered_time - dispatch_time) - sla_minutes
  IF delay_minutes > 0:
      is_delayed = TRUE
      (يُحفظ تلقائيًا في تقارير التأخير - لا حاجة لتدخل بشري)
```

**تنبيه فوري:** لو الطيار عدّى الـ SLA وهو لسه في الطريق (قبل التسليم)، السيستم يبعت إشعار للمدير فورًا "أوردر رقم X متأخر دلوقتي" بدل ما يكتشف بعد التسليم.

## 5. تدفق OTP (خطوة بخطوة)

1. الديسباتشر يؤكد خروج الأوردر → الأوردر يتحول لحالة `out_for_delivery`.
2. السيستم يولّد كود OTP فورًا (6 أرقام عشوائية حقيقية، غير متسلسلة) ويربطه بنفس الأوردر في جدول `otp_codes`، بصلاحية 15-20 دقيقة.
3. السيستم يبعت الكود للعميل بترتيب القنوات التالي (عشان يقلل التكلفة من غير ما يخسر أي عميل):
   - **أولًا:** إشعار داخل التطبيق (لو العميل مسجل ومفتوح عنده - مجاني عبر Firebase).
   - **ثانيًا:** واتساب (اختياري، يحتاج WhatsApp Business API عبر Meta أو مزود معتمد زي Twilio/360dialog - له تكلفة لكل رسالة وفترة تفعيل).
   - **أخيرًا (Fallback إجباري):** SMS - **لازم يفضل موجود كخطة احتياطية نهائية** ولا يتم إلغاؤه، لأن نسبة كبيرة من العملاء (خصوصًا الجايين من الكول سنتر) مش شرط يكونوا مسجلين بالتطبيق أو عندهم واتساب على نفس الرقم. الاعتماد الكامل على واتساب/تطبيق بس هيسيب شريحة من العملاء بدون وسيلة لاستلام الكود.
4. الطيار يوصل لعنوان العميل ويطلب الكود شفهيًا.
5. العميل يقول الكود للطيار (زي فوري/أوبر بالظبط).
6. الطيار يفتح شاشة "تأكيد التسليم" في تطبيقه ويكتب الكود.
7. السيستم يتحقق من الكود مقابل `otp_codes` الخاص بنفس الأوردر:
   - صح ومطابق ولسه في الصلاحية → الأوردر يتحول `delivered`، ويُسجَّل `delivered_time`.
   - غلط → رسالة خطأ + محاولة تانية (حد أقصى 3 محاولات، بعدها يُعلَّم الأوردر كـ "مشكلة تسليم" ويُبعت تنبيه فوري للمدير).

### حالات استثنائية لازم تتغطى في تصميم شاشة الطيار

| الموقف | الحل |
|---|---|
| العميل مش رد على الرسالة أو مش فاتح التطبيق | الكود موجود في رسالة الـ SMS نفسها، العميل يقرا الرسالة ويقول الرقم من غير ما يفتح حاجة |
| العميل مش موجود وقت وصول الطيار | زرار "العميل مش موجود" في تطبيق الطيار - يسجل حالة مختلفة عن التأخير الطبيعي، وتظهر في تقرير منفصل |
| الكود انتهت صلاحيته قبل ما الطيار يوصل (تأخير كبير) | زرار "إعادة إرسال الكود" يولّد كود جديد لنفس الأوردر |
| مشكلة في وصول الكود لأي سبب | زرار "اتصل بالعميل" مباشر (Click-to-call) من تطبيق الطيار |
| رقمين تليفون على نفس الأوردر (كما في نموذج الرسيت) | الكود يتبعت على الرقم الأساسي، ولو فشل الإرسال يتبعت تلقائيًا على الرقم الاحتياطي |

**ملاحظة تكلفة:** حجم 30-80 طيار يعني حجم أوردرات يومي كبير - قبل التنفيذ، يُنصح بمراجعة باقات SMS بالجملة للشركات مع مزود الخدمة (فودافون/أورنج) لتقليل التكلفة الشهرية.

## 6. الشاشات المطلوبة لكل واجهة

### تطبيق الطيار (Mobile)
1. **تسجيل دخول**
2. **قائمة الأوردرات الحالية**: كل أوردر بطاقة ملونة (أخضر = في الوقت، أحمر = متأخر) مع عداد الوقت المتبقي/الفائت لحظة بلحظة - يظهر للطيار تلقائيًا بمجرد ما الديسباتشر يسجّل خروجه (بدون أي إدخال من الطيار نفسه). تتحدث تلقائيًا (Auto-refresh كل 10-15 ثانية أو عبر Push Notification).
3. **شاشة تفاصيل الأوردر**: عنوان العميل ورقمه (الطيار هنا مايضغطش حاجة لبدء العداد - العداد بيبدأ أصلًا من لحظة تسجيل الديسباتشر).
4. **شاشة تأكيد التسليم**: خانة إدخال كود OTP (لوحة أرقام تلقائية `inputmode="numeric"`) يطلبه الطيار من العميل شفهيًا، وحد أقصى 3 محاولات لمنع التلاعب. بجانبها 3 أزرار للحالات الاستثنائية: "العميل مش موجود"، "إعادة إرسال الكود"، "اتصل بالعميل" (Click-to-call).
5. **سجل الأداء اليومي**: عدد الأوردرات، متوسط وقت التوصيل، وعدد مرات التأخير - في بطاقات مختصرة وواضحة.

### شاشة الديسباتشر (Web/Tablet في الفرع)
دور جديد منفصل عن الطيار ومدير الفرع - الموظف اللي بيسلّم الأوردر فعليًا للطيار وقت خروجه من الفرع:
1. **اختيار الطيار** من قائمة طيارين الفرع.
2. **إدخال رقم الأوردر وسعر التوصيل بعد الضريبة** (مطبوعين على الرسيت، إدخال يدوي بسيط لضمان الدقة).
3. **تصوير الرسيت** بكاميرا الموبايل/التابلت (دليل إثبات لحظة الخروج، وليس مصدر بيانات يُقرأ آليًا).
4. **تأكيد الخروج**: بمجرد الضغط، يُسجَّل `dispatch_time` بوقت السيرفر، ويُحسب `prep_time_minutes` تلقائيًا، ويبدأ عداد التوصيل عند الطيار.

**ملاحظة تصميم:** الطيار بيستخدم التطبيق وهو على الموتوسيكل، فكل شاشاته لازم تبقى بأقل عدد خطوات ممكن وأزرار كبيرة، من غير تفاصيل زيادة.

### شاشة موظف الكول سنتر (Web)
موظف بيستقبل مكالمات العملاء وينشئ الأوردر نيابة عنهم:
1. **البحث عن العميل** برقم الموبايل - لو موجود قبل كده، تظهر بياناته وعناوينه المحفوظة تلقائيًا؛ لو عميل جديد، يدخل اسمه وعنوانه (عمارة/دور/شقة/منطقة) في نفس الشاشة.
2. **تحديد الفرع**: يظهر تلقائيًا أقرب فرع حسب منطقة العميل (قابل للتعديل يدويًا لو محتاج).
3. **تصفح المنيو وإضافة الأصناف** - نفس شاشة المنيو المستخدمة في تطبيق العميل (نفس `menu_items` و`combo_offers`).
4. **طريقة الدفع**: كاش عند الاستلام، أو تحويل انستاباي - لو تحويل، يرفع الموظف صورة إثبات التحويل اللي بعتها العميل (`payment_proof_url`) أو يدخلها العميل بنفسه لو مسجل بالتطبيق.
5. **تأكيد الطلب** → ينشئ الأوردر بحالة `pending_acceptance` و `order_source = call_center`، ويدخل نفس مسار القبول والتحضير والتوصيل المعتمد في باقي المستند.

### لوحة تيم ليدر / هيد مانجر - قبول ومتابعة الأوردرات (Web)
واجهة مشتركة لدورين (`team_leader` و`general_manager`) مسؤولة عن **البوابة المركزية لقبول الأوردرات** قبل ما تدخل مرحلة التحضير - بغض النظر عن مصدرها (كول سنتر / تطبيق العميل / كاشير):
1. **قائمة الأوردرات بانتظار القبول** (`pending_acceptance`): تفاصيل الأوردر، طريقة الدفع، وصورة إثبات التحويل لو انستاباي - مع زرين "قبول" و"رفض" لكل أوردر.
2. **عداد سريع أعلى الشاشة**: عدد الأوردرات المقبولة اليوم، وتوزيعها على كل فرع من الـ13 فرع (كام أوردر لكل فرع).
3. **متابعة حية لكل الأوردرات الجارية** (بعد القبول) عبر كل الفروع - نفس فكرة Dashboard المدير لكن مركّزة على القبول والتوزيع مش على إدارة المستخدمين.

**ملاحظة:** لو الأوردر جاي من الكاشير مباشرة (Deyafa) بدون مراجعة كول سنتر، ممكن الاتفاق يكون إن أوردرات الكاشير تتقبل تلقائيًا (auto-accept) لأنها مرت أصلًا على نظام داخلي موثوق، وتبقى بوابة القبول دي مخصصة بس لأوردرات الكول سنتر وتطبيق العميل. (نقطة تحتاج تأكيد منكم قبل التنفيذ).

### موقع/تطبيق العميل (Web/PWA)
1. تسجيل/تسجيل دخول برقم الموبايل
2. الملف الشخصي (العمارة، الدور، الشقة، المنطقة)
3. **تصفح المنيو**: الأقسام (الكشري، الطواجن، الحلو، المشروبات، الإضافات) وعروض الكومبو، كل صنف بسعره وصورته.
4. **سلة الطلب (Cart)**: إضافة أصناف وكميات، وتعديلها قبل التأكيد.
5. **تأكيد الطلب (Checkout)**: اختيار العنوان المحفوظ (أو إضافة عنوان جديد)، طريقة الدفع:
   - **كاش عند الاستلام**: بدون أي خطوة إضافية.
   - **تحويل انستاباي**: تظهر شاشة برقم/QR المحول عليه، والعميل يرفع صورة إسكرين شوت التحويل (`payment_proof_url`) قبل ما يقدر يضغط "تأكيد الطلب".
   ثم ملخص السعر، ثم "تأكيد الطلب" → يُنشئ الأوردر تلقائيًا بـ `order_source = customer_app` وحالة `pending_acceptance`، ويبدأ `order_time` من هذه اللحظة.
6. **متابعة حالة الأوردر لحظة بلحظة** بمراحل واضحة:
   - **بانتظار القبول** (`pending_acceptance`) - لسه مراجعة من الفرع/التيم ليدر.
   - **جاري التحضير** (`preparing`) - بعد القبول.
   - **خرج للتوصيل** (`out_for_delivery`) - بعد تسجيل الديسباتشر.
   - **تم التسليم** (`delivered`).
7. بيانات الطيار (اسم، رقم، تقييم) - تظهر بمجرد ما الأوردر يوصل لمرحلة "خرج للتوصيل".
8. عرض الـ OTP الخاص بيه وقت التسليم
9. سجل الأوردرات السابقة (بما فيها إعادة الطلب بضغطة واحدة من أوردر سابق)

**ملاحظة مهمة:** الطلب من داخل التطبيق يدخل بنفس آلية الأوردرات القادمة من الكول سنتر أو الكاشير تمامًا (نفس جدول `orders` ونفس منطق القبول والـ SLA والتأخير) - الفرق الوحيد هو `order_source`.

### لوحة المدير (Web Dashboard)
1. Dashboard حي: عدد الأوردرات الجارية / المتأخرة (أحمر) / المسلمة اليوم
2. فلترة العرض تلقائيًا حسب الدور (بدون اختيار من المستخدم نفسه):
   - **مدير عام**: يشوف كل الـ13 فرع (مع دروب داون لو حاب يركّز على منطقة أو فرع معين).
   - **مدير منطقة**: يشوف فروع منطقته فقط (دروب داون لفروع منطقته بس).
   - **مدير فرع**: يشوف فرعه فقط (مقفول، بدون اختيار).
3. صفحة الطيارين: أداء كل طيار (عدد الأوردرات، متوسط وقت التسليم، عدد التأخيرات) - ضمن النطاق المسموح للدور.
4. صفحة الشكاوى: تسجيل ومتابعة كل شكوى - ضمن النطاق المسموح للدور.
5. التقرير اليومي: زرار "تصدير Excel/PDF" + جدولة إرسال تلقائي يومي بالإيميل - لكل فرع أو مجمّع حسب صلاحية الدور.
6. **شاشة إدارة المستخدمين**: إضافة/تعديل/تعطيل مستخدم (اسم، رقم موبايل، دور، فرع أو منطقة) - متاحة لكل من مدير عام (بلا قيود) ومدير منطقة (لفروع منطقته) ومدير فرع (لفرعه فقط)، حسب منطق الصلاحيات الموضح في القسم 3.
7. **شاشة إدارة الفروع والمناطق**: إضافة فرع جديد أو منطقة جديدة - متاحة للمدير العام فقط. تشمل أيضًا:
   - **تعيين/تغيير مدير الفرع**: اختيار مستخدم موجود (أو إنشاء واحد جديد) وربطه بفرع كـ `branch_manager` - يحل محل أي مدير سابق لنفس الفرع تلقائيًا.
   - **تعيين/تغيير مدير المنطقة**: نفس المنطق لكن بربط المستخدم بـ `region_id` كـ `regional_manager`.
   - **تعليم فرع كـ "غير متاح للتوصيل"**: تفعيل/إلغاء `is_delivery_available` لأي فرع مباشرة من نفس الشاشة.

## 7. التكامل مع الـ POS - Deyafa (Simple Touch Software)

نظام الكاشير المستخدم هو **Deyafa** من شركة **Simple Touch Software** (شركة مصرية، 26+ سنة خبرة، أكثر من 10,000 تركيب POS في مصر والخليج). الشركة معلنة رسميًا عن نظام تكامل جاهز مع منصات توصيل خارجية (طلبات، مرسول، إنستاشوب) في هَب واحد، وشراكات تقنية موثقة مع Odoo وSAP وFawry وPaymob.

**الخطوة العملية:** التواصل مع فريق دعم/مبيعات Simple Touch مباشرة والسؤال عن توفر API أو Webhook لتصدير بيانات الأوردر (رقم الأوردر، الفرع، اسم ورقم العميل، العنوان، سعر التوصيل بعد الضريبة) لحظة تسجيله كـ Delivery. بما إن الشركة أصلًا متكاملة مع منصات خارجية، هذا النوع من الطلبات متوقع ومألوف لهم.

**الخيار أ (الأفضل - لو أكدوا وجود API/Webhook):**
- Deyafa تبعت بيانات الأوردر تلقائيًا لحظة تسجيله لسيستم التوصيل الجديد عبر Webhook.
- السيستم الجديد يستقبلها ويحولها لصف جديد في جدول `orders` (بما فيها `delivery_fee_after_tax` لحساب الـ SLA تلقائيًا).

**الخيار ب (بديل - لو مفيش API متاح لحسابكم تحديدًا):**
- شاشة بسيطة داخل لوحة المدير/الكول سنتر لإدخال: رقم أوردر الكاشير + رقم موبايل العميل + الفرع + سعر التوصيل بعد الضريبة → يتولد أوردر في السيستم الجديد. خطوة واحدة إضافية (أقل من دقيقة) لموظف الكول سنتر.

**نصيحة:** لا داعي لانتظار رد Simple Touch قبل البدء - تنفيذ المرحلة 1 و2 (تطبيق الطيار ولوحة المدير) يمكن أن يعمل بشكل مستقل تمامًا عن الكاشير من اليوم الأول، ويُضاف التكامل المباشر لاحقًا سواء تأكد وجود API أو تم اعتماد الخيار البديل.
